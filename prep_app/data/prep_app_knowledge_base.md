# Полная база данных и материалов для приложения подготовки (400k+ Go / BigTech)

## 1. Утренний протокол (prep_protocol)

Утренний протокол, 35 минут, не больше.

Чётные дни — одна карточка track=dumps. Говоришь ответ вслух 5 минут, потом открываешь скелет. Не читаешь заранее.
Нечётные дни — одна карточка track=patterns. 5 минут идея, 15 минут код на Go, стоп даже если не дописал.
Воскресенье — одна карточка system_design (40 мин вслух по каркасу) или legend (15 мин, один буллет резюме).

Правило: одна карточка = один день. Не нагонять пропущенное пачкой.
Команда: python3 ~/bigtech_prep.py today
Отметить: python3 ~/bigtech_prep.py done <id>


## 2. Треки подготовки (prep_tracks)

### [dumps] Секции компаний (25 мин)
- **Зачем:** Пул вопросов в Ozon/Авито/Т-Банке повторяется. Учить весь язык бессмысленно — закрывать то, что реально спрашивают.
- **Как тренировать:** Утро, чётный день: 1 вопрос. 5 минут говоришь вслух, потом сверяешь скелет ответа. Не читать главу.

### [patterns] Алгоритмы по паттернам (25 мин)
- **Зачем:** Не 500 задач. ~14 шаблонов Blind/NeetCode. Цель — за 5 минут узнать тип и набросать решение.
- **Как тренировать:** Утро, нечётный день: 1 паттерн. Идея 5 мин, код на Go 15 мин, стоп.

### [system_design] System Design по шаблону (40 мин)
- **Зачем:** На 400к+ это решающая секция. Не импровизация, а один и тот же каркас + 5 типовых систем.
- **Как тренировать:** Раз в неделю, 40 минут: одна система вслух по каркасу. Цифры нагрузки называть сразу.

### [legend] Легенда и упаковка опыта (15 мин)
- **Зачем:** Интервьюер покупает не стек, а историю: проблема → решение → компромисс → цифра.
- **Как тренировать:** Раз в неделю 15 минут: переписать один буллет резюме. Без воды.

## 3. Консолидированные карточки Бигтеха (prep_items — 43 шт.)

### #1 [DUMPS] Ozon | Go runtime (Middle+, сложн: 3/5, слот: even)
- **Вопрос:** Чем горутина отличается от потока ОС?
- **Теория:** GMP: G=горутина, M=OS thread, P=логический процессор с локальной очередью. Модель M:N. С Go 1.14 планировщик вытесняющий (async preemption), не чисто кооперативный.
- **Скелет ответа:** Стек горутины стартует с ~2 КБ и растёт, у потока ОС — мегабайты. Тысячи горутин на горстке потоков. Переключение в userspace дешевле context switch ядра. Планировщик: work-stealing, netpoller для блокирующего I/O.
- **Источник:** Публичный разбор топ-вопросов Ozon (careerclue, 2026) + гайд h.careers (https://h.careers/interview-guides/golang-developer/ozon-razrabotchik-golang)

### #2 [DUMPS] Ozon | Go memory (Middle, сложн: 3/5, слот: even)
- **Вопрос:** Что выведет код с append слайса, переданного в функцию, и с мутацией элемента по индексу?
- **Теория:** Слайс — заголовок (ptr, len, cap), передаётся по значению. Underlying array общий, пока append не реаллоцирует.
- **Скелет ответа:** append внутри функции переприсваивает локальную копию заголовка — снаружи len не меняется, если не вернуть слайс. Запись in[i]=x меняет общий массив — снаружи видно. Если cap кончился, append выделяет новый массив и внешний слайс старый не увидит.
- **Источник:** h.careers, гайд Ozon Golang (https://h.careers/interview-guides/golang-developer/ozon-razrabotchik-golang)

### #3 [DUMPS] Ozon | Go gotchas (Middle, сложн: 2/5, слот: even)
- **Вопрос:** Почему указатели на переменную цикла range могут указывать на одно значение?
- **Теория:** До Go 1.22 переменная цикла переиспользовалась. С 1.22 — новая переменная на итерацию. На собесе всё равно спрашивают старый баг.
- **Скелет ответа:** До 1.22: for _, v := range xs { p = &v } — все указатели на одну v, в конце последнее значение. Фикс: &xs[i] или v := v. С 1.22 семантика per-iteration, но писать &xs[i] всё равно яснее.
- **Источник:** h.careers + Go 1.22 release notes (https://go.dev/blog/loopvar-preview)

### #4 [DUMPS] Ozon | Data processing (Middle, сложн: 3/5, слот: even)
- **Вопрос:** Файл логов 10 ГБ не влезает в память. Как посчитать топ-10 URL?
- **Теория:** Внешняя сортировка / хеш-агрегация чанками / unix-пайплайн. Не грузить файл целиком.
- **Скелет ответа:** Варианты: (1) потоковое чтение + map, если уникальных URL мало; (2) если map не влезает — разбить по хешу URL на файлы, посчитать каждый, смержить топы кучей; (3) sort | uniq -c | sort -nr | head. Сложность по диску, не по RAM.
- **Источник:** Habr, разбор реальных задач (Ozon, потоковая обработка лога) (https://habr.com/ru/articles/995600/)

### #5 [DUMPS] Ozon | Money / SQL (Middle+, сложн: 4/5, слот: even)

### #6 [DUMPS] Ozon | Channels (Middle, сложн: 3/5, слот: even)

### #7 [DUMPS] Avito | Payments (Senior, сложн: 4/5, слот: even)
- **Вопрос:** Как сделать идемпотентное списание в биллинге при ретраях клиента и at-least-once Kafka?
- **Теория:** Идемпотентность — свойство операции, не брокера. Kafka сама по себе не даёт exactly-once на стороне бизнеса.
- **Скелет ответа:** Клиент шлёт Idempotency-Key. Сервис пишет ключ в ту же транзакцию, что и проводку (уникальный индекс). Повтор — вернуть сохранённый результат, не проводить снова. Consumer: обрабатывать пачками, коммитить оффсет после успешной транзакции. Outbox, если надо и записать в БД, и опубликовать событие.
- **Источник:** h.careers, гайд Авито Go (реклама/биллинг, 2026) (https://h.careers/interview-guides/golang-developer/avito-go-razrabotchik)

### #8 [DUMPS] Avito | Kafka (Middle+, сложн: 3/5, слот: even)
- **Вопрос:** Партиции, consumer group, что будет если консьюмеров больше, чем партиций?
- **Теория:** Партиция — единица порядка и параллелизма. В группе одна партиция читается одним консьюмером.
- **Скелет ответа:** Лишние консьюмеры простаивают. Порядок гарантирован только внутри партиции — ключ сообщения (user_id/order_id) выбирают так, чтобы связанные события не разъехались. Ребаланс останавливает чтение; длинная обработка без коммита = повтор после рестарта.

### #9 [DUMPS] Avito | SQL (Middle, сложн: 3/5, слот: even)
- **Вопрос:** Чем отличаются уровни изоляции и когда Repeatable Read недостаточно?
- **Теория:** Аномалии: dirty read, non-repeatable read, phantom. Postgres Repeatable Read — это snapshot, не классический RR из учебника.
- **Скелет ответа:** Read Committed (дефолт PG): каждый запрос свой снимок, фантомы между запросами возможны. Repeatable Read: снимок на транзакцию. Serializable: ещё и защита от write skew; конфликт — ошибка сериализации, нужен ретрай. Для денег часто хватает явной блокировки строки, а не максимальной изоляции.

### #10 [DUMPS] Avito | SQL (Middle, сложн: 3/5, слот: even)
- **Вопрос:** Какой индекс под запрос SELECT a,b FROM t WHERE a=0 AND b>1 ORDER BY c?

### #11 [DUMPS] T-Bank | Concurrency (Middle+, сложн: 3/5, слот: even)
- **Вопрос:** Напиши worker pool: N воркеров, очередь задач, корректная остановка.
- **Теория:** Пул ограничивает параллелизм. Закрытие канала — сигнал «задач больше не будет», не «убить воркера посреди работы».

### #12 [DUMPS] T-Bank | Go runtime (Senior, сложн: 4/5, слот: even)
- **Вопрос:** Как устроен планировщик Go и что изменилось в 1.14?
- **Теория:** До 1.14 горутина без вызовов функций могла не отдавать P. С 1.14 — асинхронное вытеснение по сигналу.
- **Скелет ответа:** P держит локальную очередь (~256). Нет работы — крадёт половину у другого P, потом глобальная очередь, потом netpoller. Syscall: M отцепляется от P, P подхватывает другой M. GOMAXPROCS = число P.

### #15 [DUMPS] any | Go (Senior, сложн: 4/5, слот: even)
- **Вопрос:** nil-интерфейс и интерфейс с nil-указателем внутри — в чём разница?

## 5. Тяжелые для восприятия концепции (hard_concepts.db — 2 шт.)

### #1 [MCP & Agentic AI] MCP stdio Transport & Protocol Serialization
- **Простыми словами:** MCP (Model Context Protocol) — стандарт подключения инструментов к AI. При транспорте stdio клиент и сервер общаются через стандартные потоки ввода-вывода (stdin/stdout) процесса, как в конвейере терминала.
- **Под капотом:** Каждое сообщение строго сериализуется в JSON-RPC 2.0 (одна строка — один JSON-объект). Клиент пишет вызовы методов в stdin сервера, а сервер пишет ответы строго в свой stdout.
- **Подводные камни:** Случайный print/логирование в stdout (например fmt.Println("debug")) ломает парсер клиента ошибкой JSON parse error. Все отладочные логи в MCP обязаны идти исключительно в stderr!

### #2 [Electron & Desktop Security] Electron IPC: preload.js and contextBridge
- **Простыми словами:** В Electron веб-интерфейс (React) изолирован от операционной системы ради безопасности. preload.js и contextBridge создают строго контролируемый мост для вызова системных функций из браузера.
- **Под капотом:** Рендерер (Chromium) работает в песочнице без прямого доступа к require("fs") или child_process. В файле preload.js через contextBridge.exposeInMainWorld("myAPI", { ... }) в глобальный объект window добавляются только явно разрешенные методы, отправляющие IPC-сообщения (ipcRenderer.invoke) в Главный процесс (Node.js).
- **Подводные камни:** Включение nodeIntegration: true дает интерфейсу прямой доступ к Node.js. Любая XSS-уязвимость в веб-странице или подгруженном скрипте превращается в мгновенное выполнение произвольного вредоносного кода на компьютере пользователя (RCE).

### Q#1 [Go / Data Structures] (Junior, сложн: 2/5) — ⏳ Не отвечен
- **Вопрос:** Как устроен slice внутри и что происходит при вызове append, если cap превышена?
- **Эталонный ответ:**
Slice представляет собой трехсловную структуру (slice header): указатель на массив (unsafe.Pointer), длина len (int) и емкость cap (int). При превышении cap аллоцируется новый массив в памяти большего размера (в Go 1.18+ для малых слайсов удваивается, для больших растет плавно примерно на 1.25x), данные копируются, и возвращается новый slice header.
- **Источник:** goavengers/go-interview

### Q#2 [Go / Data Structures] (Middle, сложн: 3/5) — ⏳ Не отвечен
- **Вопрос:** Как устроена map под капотом в Go? Потокобезопасна ли она?
- **Эталонный ответ:**
Map реализована как хеш-таблица с бакетами (структура hmap). Каждый бакет (bmap) хранит до 8 пар ключ-значение. При коэффициенте заполнения > 6.5 или переполнении бакетов происходит эвакуация (рост таблицы в 2 раза) инкрементально при операциях записи/удаления. Map НЕ является потокобезопасной; одновременная запись и чтение без блокировок вызывает фатальную панику (concurrent map read and map write). Для конкурентного доступа используют sync.RWMutex или sync.Map.
- **Источник:** goavengers/go-interview

### Q#3 [Go / Concurrency] (Senior, сложн: 4/5) — ⏳ Не отвечен
- **Вопрос:** Как работает планировщик Go (GMP модель)?
- **Эталонный ответ:**
Планировщик Go использует модель GMP: G (Goroutine — стек, регистры, статус), M (OS Thread — системный поток ОС), P (Processor — контекст выполнения, очередь горутин). У каждого P есть локальная очередь (runqueue) на 256 горутин и глобальная очередь. Планировщик использует алгоритм work-stealing (если у P закончились горутины, он крадет половину у другого P) и сетевой поллер (NetPoller) для неблокирующего ввода-вывода.
- **Источник:** Devinterview-io

### Q#4 [Go / Concurrency] (Junior, сложн: 2/5) — ⏳ Не отвечен
- **Вопрос:** Что произойдет при чтении и записи в nil и закрытый канал?
- **Эталонный ответ:**
1) nil-канал: чтение и запись блокируют горутину навсегда (deadlock); закрытие nil-канала вызывает panic.
2) Закрытый канал: запись вызывает panic; чтение возвращает zero value типа канала и false во втором параметре (val, ok := <-ch); повторное закрытие вызывает panic.
- **Источник:** Standard Go Specification

### Q#5 [Go / Memory & Runtime] (Middle, сложн: 3/5) — ⏳ Не отвечен
- **Вопрос:** Что такое Escape Analysis (анализ побега) в Go?
- **Эталонный ответ:**
Это оптимизация компилятора, определяющая, где выделить память под переменную — на стеке или в куче. Если ссылка на переменную 'убегает' за пределы текущей функции (возврат указателя, отправка в канал, передача в интерфейс any), она аллоцируется в куче (heap) и будет управляться сборщиком мусора (GC). Иначе — на быстром стеке (stack). Проверяется флагом go build -gcflags='-m'.
- **Источник:** Go Runtime Internals

### Q#6 [Go / Memory & Runtime] (Senior, сложн: 5/5) — ✅ Отвечен
- **Вопрос:** Как устроен Garbage Collector (сборщик мусора) в Go?
- **Эталонный ответ:**
GC в Go — это параллельный, некомпактифицирующий, трехцветный (tri-color mark-and-sweep) сборщик мусора. Объекты маркируются цветами: Белый (кандидат на удаление), Серый (достижим, но связи не проверены), Черный (достижим, все ссылки проверены). Использует короткие паузы Stop-The-World (STW) только для инициализации и завершения маркировки (обычно < 1 мс), а основная фаза маркировки выполняется конкурентно с помощью Write Barrier.
- **Заметки пользователя:** Хорошее понимание. Уточнить: 1) Черные = живые и проверенные, Белые = мусор; 2) Трассировка графа (Tracing GC), а не подсчет ссылок (Reference counting).
- **Источник:** Go Runtime Internals

### Q#7 [Flutter/Dart / Dart Basics] (Middle, сложн: 3/5) — ⏳ Не отвечен
- **Вопрос:** В чем разница между Event Loop, Microtask Queue и Event Queue в Dart?
- **Эталонный ответ:**
Dart однопоточен и обрабатывает асинхронные задачи через Event Loop с двумя очередями:
1. Microtask Queue — очередь с наивысшим приоритетом (внутренние задачи Dart, scheduleMicrotask). Event loop не перейдет к событиям, пока очередь микротасок не опустеет.
2. Event Queue — очередь внешних событий (Future, таймеры, ввод пользователя, I/O, сообщения из изолятов).

### Q#13 [Networking / HTTP Versions] (Middle, сложн: 4/5) — ⏳ Не отвечен
- **Вопрос:** В чем ключевые различия между HTTP/1.0, HTTP/1.1, HTTP/2 и HTTP/3 (QUIC)?
- **Эталонный ответ:**
1. HTTP/1.0: Одно TCP-соединение на каждый запрос/ответ (высокий оверхед на рукопожатия).
2. HTTP/1.1: Появился Keep-Alive (повторное использование TCP-соединения), chunked transfer encoding, pipelining (который страдал от Head-of-Line Blocking на уровне HTTP), обязательный заголовок Host.
3. HTTP/2: Бинарный протокол (вместо текстового), мультиплексирование запросов/ответов внутри одного TCP-соединения по потокам (streams), сжатие заголовков (HPACK), Server Push. Проблема: Head-of-Line Blocking на уровне TCP (потеря одного пакета тормозит все потоки).
4. HTTP/3: Работает поверх UDP через протокол QUIC. Решает проблему HoL Blocking на уровне транспорта (каждый поток изолирован), ускоренное 0-RTT/1-RTT рукопожатие со встроенным TLS 1.3, миграция соединения при смене IP/Wi-Fi (Connection ID).
- **Источник:** RFC 9114 / High Performance Browser Networking

### Q#15 [Networking / HTTP Methods & Idempotency] (Junior, сложн: 2/5) — ✅ Отвечен
- **Вопрос:** В чем разница между безопасными (Safe) и идемпотентными (Idempotent) HTTP-методами? Может ли GET иметь тело?
- **Эталонный ответ:**
1. Safe (Безопасные): не изменяют состояние сервера при вызове (GET, HEAD, OPTIONS).
2. Idempotent (Идемпотентные): N одинаковых запросов приводят к такому же состоянию сервера, как и 1 запрос (GET, HEAD, PUT, DELETE, OPTIONS). POST и PATCH — НЕ идемпотентны (хотя PATCH можно спроектировать идемпотентным).
3. Тело в GET: по спецификации RFC тело в GET не запрещено, но не имеет определенной семантики. Большинство прокси, кэшей и веб-серверов либо игнорируют тело GET-запроса, либо отклоняют его с ошибкой 400, поэтому передавать тело в GET не рекомендуется.
- **Заметки пользователя:** Хороший ответ. Запомнить: Идемпотентность — это про конечное СОСТОЯНИЕ сервера (side-effects), а не про кэш или неизменность тела ответа.
- **Источник:** RFC 9110 (HTTP Semantics)

### Q#16 [Networking / Cookies & Web Security] (Middle, сложн: 3/5) — ⏳ Не отвечен
- **Вопрос:** Как устроены Cookies? Что делают флаги HttpOnly, Secure, SameSite и Domain/Path?
- **Эталонный ответ:**
Cookie — это механизм хранения состояния на клиенте через заголовок ответа 'Set-Cookie' и отправки в запросе 'Cookie: name=val'.

### Q#17 [Networking / TCP] (Senior, сложн: 4/5) — ⏳ Не отвечен
- **Вопрос:** Как работает трехстороннее рукопожатие (3-way Handshake) и завершение соединения (4-way Teardown) в TCP? Зачем нужно состояние TIME_WAIT?
- **Эталонный ответ:**
1. 3-way Handshake (Установка):
   - Клиент -> SYN (Seq=X)
   - Сервер -> SYN-ACK (Seq=Y, Ack=X+1)
   - Клиент -> ACK (Seq=X+1, Ack=Y+1). Соединение переходит в ESTABLISHED.
2. 4-way Teardown (Завершение):
   - Инициатор -> FIN; Ответчик -> ACK (полузакрытое соединение).
   - Ответчик -> FIN; Инициатор -> ACK.
3. TIME_WAIT (2*MSL — Maximum Segment Lifetime):
   Инициатор закрытия удерживает сокет в состоянии TIME_WAIT (обычно 1-2 мин), чтобы:
   а) Гарантировать, что последний ACK дошел до ответчика (если потеряется, ответчик перешлет FIN);
   б) Защитить новые соединения с теми же IP:Port от запоздавших пакетов из старого соединения.
- **Источник:** TCP/IP Illustrated (W. Richard Stevens)

### Q#18 [Networking / TCP] (Senior, сложн: 5/5) — ⏳ Не отвечен
- **Вопрос:** Как в TCP устроены механизмы надежности, контроля потока (Flow Control) и контроля перегрузки (Congestion Control)?
- **Эталонный ответ:**
1. Надежность: порядковые номера (Sequence Numbers), подтверждения (ACK), таймеры повторной передачи (RTO) и Fast Retransmit (3 дублирующих ACK).
2. Flow Control (Контроль потока получателя): предотвращает переполнение буфера получателя. Получатель сообщает в TCP-заголовке доступный размер окна (Window Size). Если окно 0 (Zero Window), отправитель ждет с помощью probe-пакетов.
3. Congestion Control (Контроль перегрузки сети): предотвращает переполнение каналов связи (буферов маршрутизаторов).
   Алгоритмы (Reno, Cubic, BBR) управляют окном перегрузки (cwnd):
   - Slow Start (экспоненциальный рост cwnd до ssthresh);
   - Congestion Avoidance (линейный рост);
   - Fast Recovery при потере пакетов.
- **Источник:** TCP/IP Illustrated / Computer Networking: A Top-Down Approach

### Q#19 [Networking / TCP vs UDP] (Junior, сложн: 2/5) — ⏳ Не отвечен

Отличия:
1. TCP: протокол с установкой соединения (connection-oriented), надежный (гарантия доставки и порядка байт), потоковый (stream of bytes), имеет контроль перегрузки и потока, тяжелый заголовок (от 20 байт).

- Multicast/Broadcast рассылка;
- Собственные протоколы поверх UDP с кастомным контролем надежности (QUIC / HTTP/3, WebRTC).

### Q#25 [DataScience / ML / Validation & Metrics] (Middle, сложн: 3/5) — ⏳ Не отвечен
- **Вопрос:** В каких случаях стоит использовать ROC-AUC, а когда PR-AUC (Precision-Recall AUC)?
- **Эталонный ответ:**
ROC-AUC чувствителен к True Negative Rate (FPR = FP / (FP + TN)). При сильном дисбалансе классов (например, фрод 0.1%) TN огромен, из-за чего FPR остается около 0, а ROC-AUC показывает оптимистичные 0.99 при плохом качестве детекции.
PR-AUC не зависит от TN и фокусируется только на мажоритарном/миноритарном положительном классе (Precision = TP/(TP+FP), Recall = TP/(TP+FN)), поэтому на сильно несбалансированных данных используют PR-AUC.

### Q#26 [DataScience / ML / Experimentation & A/B] (Senior, сложн: 4/5) — ⏳ Не отвечен
- **Вопрос:** Что такое CUPED в A/B-тестировании и как он снижает дисперсию?
- **Эталонный ответ:**
CUPED (Controlled-experiment Using Pre-Experiment Data) использует исторические данные о пользователях до начала теста (ковариату X) для корректировки целевой метрики Y: Y_cuped = Y - θ * (X - E[X]), где θ = Cov(Y, X) / Var(X).
Это снижает дисперсию метрики на величину (1 - ρ^2), где ρ — корреляция между X и Y. Снижение дисперсии позволяет сократить длительность теста или детектировать меньший MDE при том же объеме выборки.

2. Нормализация (BatchNorm, LayerNorm, RMSNorm);
3. Активации без насыщения (ReLU, GELU, SwiGLU);
4. Инициализация весов (He, Xavier);

### Q#28 [DeepLearning / Architecture & Normalization] (Senior, сложн: 4/5) — ⏳ Не отвечен
- **Вопрос:** В чем разница между BatchNorm и LayerNorm, и почему в Transformer используют LayerNorm?
- **Эталонный ответ:**
BatchNorm нормализует каждый признак по всему батчу (N, C, H, W -> нормализация по N). Он зависит от размера батча и плохо работает при малом batch size и переменной длине последовательностей в NLP.
LayerNorm нормализует все признаки одного сэмпла/токена независимо от других элементов батча (нормализация по C/скрытому размеру hidden_dim).
В Transformers входные тексты имеют разную длину и батчи часто динамические, поэтому LayerNorm (и его упрощенная быстрая версия RMSNorm) работает стабильнее и не требует межбатчевой статистики.

### Q#29 [LLM / Attention & Architecture] (Senior, сложн: 4/5) — ⏳ Не отвечен
- **Вопрос:** Как устроен KV-Cache в инференсе LLM и почему он необходим?
- **Эталонный ответ:**
В авторегрессионной генерации модель генерирует токены по одному. Без кэша для генерации n-го токена пришлось бы заново вычислять векторы Key и Value для всех предыдущих (n-1) токенов во всех слоях внимания (сложность O(N^2)).
KV-Cache сохраняет вычисленные матрицы K и V для прошлых токенов в памяти GPU. Для нового токена вычисляется только его Query (и один новый K, V), что делает шаг генерации O(1) по вычислениям ценой расхода VRAM.
Объем памяти KV-Cache = 2 * n_layers * n_heads_kv * head_dim * seq_len * batch_size * bytes_per_element.
- **Источник:** vLLM & HuggingFace Core

### Q#30 [LLM / Fine-Tuning (PEFT)] (Senior, сложн: 4/5) — ⏳ Не отвечен
- **Вопрос:** Как работает LoRA (Low-Rank Adaptation) и в чем отличие QLoRA?
- **Эталонный ответ:**
LoRA замораживает базовые веса W (d x k) и добавляет обучаемую низкоранговую декомпозицию ΔW = B * A, где A имеет размер (r x k), а B — (d x r), при ранге r << min(d, k). Градиенты и состояние оптимизатора считаются только для A и B, что снижает расход VRAM на 70-80%.
QLoRA идет дальше: базовые веса квантуются в 4-битный формат NF4 (NormalFloat4), используется двойная квантизация (Double Quantization) масштабирующих коэффициентов и Paged Optimizers для предотвращения OOM при пиках в памяти.
- **Источник:** LoRA / QLoRA Papers

### Q#31 [LLM / Attention Variants] (Senior, сложн: 4/5) — ⏳ Не отвечен
- **Вопрос:** В чем разница между MHA, MQA и GQA (Multi-Head, Multi-Query, Grouped-Query Attention)?
- **Эталонный ответ:**
1. MHA (Multi-Head Attention): у каждой головы внимания свои собственные проекции Q, K, V. Максимальное качество, но огромный размер KV-Cache.
2. MQA (Multi-Query Attention): у всех голов внимания один общий K и один общий V (только Q разбит на головы). Экономит KV-Cache в число голов раз, но может деградировать качество.
3. GQA (Grouped-Query Attention): компромисс (используется в Llama 2/3, Mistral). Головы Q разбиты на группы (например, 8 групп), и каждая группа делит между собой один набор K и V. Сохраняет качество MHA при существенной экономии памяти KV-кэша.

### Q#33 [MLOps / Data Drift & Monitoring] (Middle, сложн: 3/5) — ⏳ Не отвечен
- **Вопрос:** В чем разница между Data Drift, Concept Drift и Covariate Shift?
- **Эталонный ответ:**
1. Covariate Shift / Data Drift: изменение распределения входных признаков P(X), при этом зависимость P(Y|X) остается прежней (например, изменился демографический состав пользователей).
2. Concept Drift: изменение статистической взаимосвязи между признаками и целевой переменной P(Y|X), даже если P(X) не изменился (например, поведение мошенников изменилось во время кризиса).
3. Prior Probability Drift: сдвиг априорного распределения таргета P(Y).
Детектируются тестами Колмогорова-Смирнова (KS-test), Population Stability Index (PSI) и Wasserstein distance.

### Q#39 [Math & Calculus / Linear Algebra] (Middle, сложн: 3/5) — ⏳ Не отвечен
- **Вопрос:** Что такое собственные значения (Eigenvalues) и собственные векторы (Eigenvectors), и как они используются в PCA (SVD)?
- **Эталонный ответ:**
Собственный вектор матрицы A — это ненулевой вектор v, направление которого не меняется при умножении на A: A * v = λ * v, где λ — собственное значение (масштабирующий коэффициент).
В PCA (Principal Component Analysis) собственные векторы ковариационной матрицы данных X^T * X задают направления главных компонент (направления максимальной дисперсии), а собственные значения λ_i пропорциональны доле объясненной дисперсии вдоль соответствующего вектора. В сингулярном разложении (SVD: X = U * Σ * V^T) правые сингулярные векторы V являются собственными векторами X^T * X, а сингулярные числа σ_i = sqrt(λ_i).
- **Источник:** MIT 18.06 Linear Algebra / Gilbert Strang

### Q#40 [Math & Calculus / Linear Algebra & Matrix Decompositions] (Senior, сложн: 4/5) — ⏳ Не отвечен
- **Вопрос:** В чем разница между спектральным разложением (Eigendecomposition), QR-разложением и SVD (Singular Value Decomposition)?
- **Эталонный ответ:**
1. Eigendecomposition (A = Q * Λ * Q^-1): применимо только к квадратным матрицам; если матрица симметрична, Q ортогональна (Q^-1 = Q^T).
2. QR-decomposition (A = Q * R): факторизация любой матрицы на ортогональную Q (Q^T * Q = I) и верхнетреугольную R. Применяется для решения задачи наименьших квадратов и вычисления собственных чисел (QR-алгоритм).
3. SVD (A = U * Σ * V^T): универсально для матриц любого размера (m x n). U (m x m) и V (n x n) ортогональны, Σ — диагональная с неотрицательными сингулярными числами. Применяется в редукции размерности, сжатии матриц (Low-Rank Approximation по теореме Эккарта-Янга) и рекомендательных системах.
- **Источник:** Matrix Computations (Golub, Van Loan)

### Q#41 [Math & Calculus / Multivariate Calculus & Optimization] (Senior, сложн: 4/5) — ⏳ Не отвечен
- **Вопрос:** Что такое Градиент, Гессиан (Hessian) и матрица Якоби (Jacobian)? Как они используются в методах оптимизации 1-го и 2-го порядка?
- **Эталонный ответ:**
1. Градиент (∇f) — вектор частных производных скалярной функции f: R^n -> R. Указывает направление наискорейшего роста функции. Используется в методах 1-го порядка (Gradient Descent, Adam, SGD).
2. Матрица Якоби (J) — матрица частных производных вектор-функции f: R^n -> R^m (размер m x n), описывающая локальное линейное преобразование. Используется при дифференцировании слоев нейросетей (Chain Rule).
3. Матрица Гессиана (H) — квадратная матрица вторых частных производных скалярной функции f: R^n -> R (размер n x n), описывающая локальную кривизну. В методе Ньютона (2-й порядок) шаг обновления равен: x_{t+1} = x_t - H^-1 * ∇f. Это обеспечивает квадратичную сходимость, но вычисление и обращение H требует O(n^3) операций, поэтому на практике используют квазиньютоновские методы (L-BFGS).
- **Источник:** Convex Optimization (Boyd)

### Q#42 [Math & Calculus / Probability Theory & Statistics] (Middle, сложн: 3/5) — ⏳ Не отвечен
- **Вопрос:** В чем суть теоремы Байеса и разница между Maximum Likelihood Estimation (MLE) и Maximum A Posteriori (MAP)?
- **Эталонный ответ:**
Теорема Байеса: P(θ|D) = (P(D|θ) * P(θ)) / P(D), где P(θ|D) — апостериорная вероятность, P(D|θ) — правдоподобие (Likelihood), P(θ) — априорная вероятность (Prior).
1. MLE (Оценка максимального правдоподобия): находит параметры θ, максимизирующие правдоподобие данных: θ_MLE = argmax P(D|θ). Предполагает равномерный/неинформативный prior.
2. MAP (Оценка максимума апостериорной вероятности): учитывает априорные знания о распределении параметров: θ_MAP = argmax P(D|θ) * P(θ) = argmax [log P(D|θ) + log P(θ)].
Связь с ML: регуляризация в ML эквивалентна MAP. Например, L2-регуляризация (Ridge) — это MAP с гауссовским априорным распределением весов N(0, σ^2), а L1-регуляризация (Lasso) — это MAP с априорным распределением Лапласа Laplace(0, b).
- **Источник:** Pattern Recognition and Machine Learning (Bishop)

### Q#43 [Math & Calculus / Information Theory] (Middle, сложн: 3/5) — ⏳ Не отвечен
- **Вопрос:** Что такое Энтропия Шеннона, Кросс-энтропия и Дивергенция Кульбака-Лейблера (KL-divergence)?
- **Эталонный ответ:**
1. Энтропия Шеннона: H(P) = -∑ P(x) * log P(x) — мера неопределенности/хаоса случайной величины или минимальное среднее число бит для кодирования события.
2. Кросс-энтропия: H(P, Q) = -∑ P(x) * log Q(x) — средняя длина сообщения, если истинное распределение P кодируется распределением модели Q. Широко используется как Loss-функция классификации.
3. KL-дивергенция: D_KL(P || Q) = ∑ P(x) * log(P(x) / Q(x)) = H(P, Q) - H(P) — мера различия (расстояние) между распределениями P и Q. Несимметрична (D_KL(P||Q) != D_KL(Q||P)). Ключевой компонент в VAE (ELBO loss) и Alignment LLM (RLHF/DPO penalization за отклонение от базовой модели).
- **Источник:** Elements of Information Theory (Cover & Thomas)

### Q#44 [Graph Theory / Traversal & Shortest Path] (Middle, сложн: 3/5) — ⏳ Не отвечен
- **Вопрос:** В чем разница между алгоритмами Дейкстры, Беллмана-Форда, Флойда-Уоршелла и A*?

1. Алгоритм Дейкстры: ищет кратчайшие пути от одного источника (SSSP) во взвешенном графе с НЕОТРИЦАТЕЛЬНЫМИ весами. Сложность с бинарной/фибоначчиевой кучей: O((V + E) log V).

3. Флойд-Уоршелл: ищет кратчайшие пути между ВСЕМИ парами вершин (APSP). Динамическое программирование. Сложность: O(V^3).

### Q#45 [Graph Theory / Topology & Structural Analysis] (Middle, сложн: 3/5) — ⏳ Не отвечен
- **Вопрос:** Что такое Топологическая сортировка, Сильно связанные компоненты (SCC) и мосты/шарниры в графе?
- **Эталонный ответ:**
1. Топологическая сортировка: линейное упорядочивание вершин направленного ациклического графа (DAG), где для каждого ребра (u, v) u предшествует v. Алгоритмы: DFS (по времени выхода) или Kahn (на основе входящих степеней in-degree). Сложность O(V + E). Применяется в Task Schedulers (Airflow, Build-системы).
2. Сильно связанные компоненты (SCC): максимальные подграфы ориентированного графа, где между любыми двумя вершинами есть путь в обе стороны. Алгоритмы: Косарайю (2 прохода DFS) или Тарьяна (1 проход DFS со стеком и lowlink).
3. Мосты (Bridges) и Точки сочленения (Articulation Points / Шарниры): ребра и вершины, удаление которых увеличивает число компонент связности графа (критические точки отказа в сетях). Находятся за O(V + E) с помощью DFS.

### Q#46 [Graph Theory / Graph Neural Networks & Embeddings] (Senior, сложн: 4/5) — ⏳ Не отвечен
- **Вопрос:** Как работает агрегация сообщений (Message Passing) в графовых нейронных сетях (GCN, GAT, GraphSAGE)?
- **Эталонный ответ:**
В Message Passing фреймворке эмбеддинг вершины h_v на слое (k+1) обновляется на основе агрегации представлений ее соседей N(v):
1. Message: вычисляются сообщения m_{u->v} = Msg(h_u^(k), h_v^(k), e_{uv}).
2. Aggregate: сообщения соседей агрегируются перестановочно-инвариантной функцией (SUM, MEAN, MAX): a_v^(k) = Agg({m_{u->v} : u ∈ N(v)}).
3. Update: h_v^(k+1) = Update(h_v^(k), a_v^(k)).
Различия архитектур:
- GCN (Graph Convolutional Networks): нормализованное усреднение соседей со статическими весами графа (D^{-1/2} A D^{-1/2}).
- GAT (Graph Attention Networks): использует механизм внимания (Self-Attention) для назначения обучаемых динамических весов важности соседям.
- GraphSAGE: сэмплирует фиксированное число соседей и использует обучаемые функции агрегации (LSTM, Pooling), что позволяет делать индуктивный инференс на больших графах.
- **Источник:** Stanford CS224W: Machine Learning with Graphs

### Q#47 [Graph Databases / Data Models & Architecture] (Middle, сложн: 3/5) — ⏳ Не отвечен
- **Вопрос:** В чем разница между Labeled Property Graph (LPG) и Resource Description Framework (RDF/Triple Store)?
- **Эталонный ответ:**
1. Labeled Property Graph (LPG, например Neo4j, Memgraph, Amazon Neptune):

   - Стандартизирован W3C для Semantic Web (включает онтологии OWL, схему RDFS).
   - Язык запросов: SPARQL. Оптимизирован для формального логического вывода (Inference / Reasoning), интеграции распределенных данных и Knowledge Graphs.
- **Источник:** Graph Databases (O'Reilly / Ian Robinson)

### Q#48 [Graph Databases / Storage & Index-Free Adjacency] (Senior, сложн: 4/5) — ⏳ Не отвечен
- **Вопрос:** Что такое Index-Free Adjacency (безиндексная смежность) в Native Graph БД и чем она отличается от графовых запросов в RDBMS?
- **Эталонный ответ:**
1. Index-Free Adjacency (IFA): каждая нода на физическом уровне хранит прямые указатели (память/дисковые смещения) на свои инцидентные ребра и соседние ноды. Обход графа (Graph Traversal) сводится к разыменованию указателей (pointer chasing) со сложностью O(k), где k — степень вершины, и НЕ зависит от общего размера графа N.
2. В RDBMS / Non-native Graph: связи между таблицами моделируются через Foreign Keys. Для каждого шага обхода (Join) СУБД должна искать строки во вторичных B-Tree / Hash индексах. Сложность выполнения растет логарифмически или полиномиально от общего объема базы: O(k * log N). На глубине 4-5 JOIN'ов классическая реляционная БД деградирует по производительности.
- **Источник:** Neo4j Internals & Architecture

### Q#49 [Graph Databases / Query Languages & Cypher] (Middle, сложн: 3/5) — ⏳ Не отвечен
- **Вопрос:** Как устроен язык Cypher (declarative graph querying) и как оптимизируются графовые паттерны?
- **Эталонный ответ:**
Cypher использует ASCII-art синтаксис для визуализации шаблонов: `(node:Label)-[:REL_TYPE]->(target:Label)`.
Пример сложного поиска: `MATCH (u:User {id: $id})-[:FRIEND*1..2]-(f:User)-[:LIKES]->(p:Product) WHERE NOT (u)-[:BOUGHT]->(p) RETURN p.name, count(*) AS score ORDER BY score DESC LIMIT 10`.
Оптимизатор запросов (Query Planner):
1. Выбирает стартовую ноду с наименьшей кардинальностью (Anchor Node) с использованием Node Index / Schema Index.
2. Expand: последовательное раскрытие связей через IFA.
3. Filter / Join: фильтрация по предикатам и объединение ветвей поиска.
4. Проверка изоморфизма путей (по умолчанию Cypher гарантирует Relationship Uniqueness — одно и то же ребро не проходится дважды в одном MATCH).
- **Источник:** Neo4j Cypher Manual

### Q#50 [Graph Databases / GraphRAG & Knowledge Graphs] (Senior, сложн: 5/5) — ⏳ Не отвечен
- **Вопрос:** Что такое GraphRAG и в чем его преимущество перед классическим Vector RAG?
- **Эталонный ответ:**
1. Проблема Vector RAG: семантический поиск по эмбеддингам чанков находит локально похожие фрагменты, но теряет глобальный контекст и не способен связывать многошаговые сущности (Multi-hop reasoning across documents) или отвечать на глобальные вопросы типа 'Какие ключевые темы связывают все документы?'.
2. GraphRAG (Microsoft / Neo4j):
   - Из документов с помощью LLM извлекаются сущности, связи и их описания, формируя Knowledge Graph (Граф Знаний).
   - Ноды кластеризуются графовыми алгоритмами (Leiden / Louvain community detection) с генерацией сводных отчетов по сообществам на разных уровнях иерархии.
   - При запросе выполняется комбинированный поиск: локальный поиск по графу связей сущностей + глобальный поиск по иерархическим саммари сообществ, что кардинально повышает качество ответов и снижает галлюцинации.
- **Источник:** Microsoft Research GraphRAG Paper

### Q#51 [Networking / HTTP & REST API] (Middle, сложн: 3/5) — ⏳ Не отвечен
- **Вопрос:** В чем разница между методами PUT и PATCH? Как правильно реализовать идемпотентный PATCH?
- **Эталонный ответ:**
1. PUT предназначен для полной замены ресурса (Full Replacement). Клиент присылает полное новое состояние объекта. Если ресурса нет, он создается, либо перезаписывается целиком. Метод идемпотентен по спецификации.
2. PATCH предназначен для частичного обновления (Partial Update). Клиент отправляет только те поля, которые нужно изменить. По спецификации PATCH НЕ является идемпотентным (например, операция 'добавить 5 к счетчику' при каждом вызове меняет состояние).
3. Идемпотентный PATCH можно реализовать через:
   - Передачу абсолютных значений полей (например, { 'status': 'active' } вместо инкрементов);
   - Стандарт JSON Patch (RFC 6902) или JSON Merge Patch (RFC 7396);
   - Использование заголовка If-Match с ETag (optimistic concurrency control) или уникального Idempotency-Key.
- **Источник:** RFC 5789 / REST API Design

### Q#52 [Networking / HTTP Status Codes & Headers] (Junior, сложн: 2/5) — ⏳ Не отвечен
- **Вопрос:** Каковы различия между кодами редиректа 301, 302, 307 и 308?
- **Эталонный ответ:**
1. 301 (Moved Permanently) vs 308 (Permanent Redirect):
   - 301: Постоянный редирект, но исторически браузеры меняли метод с POST на GET при переходе.
   - 308: Постоянный редирект со СТРОГИМ сохранением метода и тела запроса (POST остается POST).
2. 302 (Found) vs 307 (Temporary Redirect):
   - 302: Временный редирект, исторически меняет метод на GET.
   - 307: Временный редирект со СТРОГИМ сохранением метода и тела запроса.
307 и 308 были введены в HTTP/1.1 (RFC 7231 / RFC 7538), чтобы исправить двусмысленность 301/302.
- **Источник:** MDN Web Docs / RFC 7538
